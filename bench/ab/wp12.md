## Render-cap decision (flagged, not silent)

The mission brief scales WP12's acceptance to 2 real videos and names this
as the **last** of the owner's 2026-09-30 2-render cap (1 already spent on
WP10's `tunguska_1908` real render). The brief's own instruction: if
unsure whether to spend it, prefer fixtures and defer, with a clear note.

I am not unsure here — I'm confident a real run would very likely HOLD/FAIL
again, for reasons that have nothing to do with WP12's own correctness and
everything to do with gaps `bench/ab/wp10.md` already found and no WP
between WP10 and WP12 has touched:

1. **Hook timing is a deterministic, story-independent miss.**
   `v15_pipeline.py`'s own `LEAD_S = 0.30` (silence before each beat's
   narration) is *larger* than `v16_gate.check_hook`'s own 0.25s first-word
   bound — the first word of a video using the default lead cannot land
   before 0.30s no matter what story runs. WP10's real render failed this
   exact check (`first word at 0.31s > the 0.25s bound`). This isn't
   topic-specific noise; it is a constant vs. a gate bound, still
   contradictory in the code today.
2. **Voice WER (0.0542 > the 0.03 gate)** and **caption safe-zone** (a
   caption-box y-position case WP6/WP7's fixes didn't cover) were both
   real, reproducible failures on WP10's render, on the shared Kokoro
   voice/caption-layout code every story goes through — not shown to be
   story-specific, and not in scope for any WP between WP10 and WP12
   (WP8 = images, WP11 = topics, WP5 = a Remotion path still uncalled).
3. Spending the last slot on a run very likely to HOLD for already-known,
   already-documented reasons would burn the cap without adding
   information — the owner already has the itemized FAIL table from
   WP10's render.

So: the real-render acceptance line is **deferred**, not attempted. What
*is* real below: preflight against the live environment, one small (~$0.06,
2 LLM calls — a topic-selection cost, not a video-render cost, same
category WP11 already spent live) `select_topics` call, and `package_video`
run for real (`ffmpeg`, not mocked) against an already-existing
`build/v15/ice_slippery/final.mp4` from an earlier render (packaging is
pure post-processing — it spends no part of the render cap, however many
times it runs). The pause/resume control flow itself is proven with a
fixture per the brief's own explicit allowance ("no real render needed for
this").

**Recommendation for whoever spends the last render slot**: fix #1 above
first (`LEAD_S` vs. the hook-timing gate bound are two numbers in the same
codebase that cannot both be satisfied) — otherwise the last slot's render
will very likely reproduce WP10's same hook-timing FAIL for a reason that
was already diagnosable from the code alone, without spending it.

## Lanes — flagged as not implemented, not silently skipped

See `CHANGELOG.md`'s WP12 entry and the module docstring for the full
reasoning: DESIGN §1.2's staged S0-S14 pipeline (one artifact + `.done`
marker per stage, the thing that would let video k+1's S1-S7 run while
video k holds an S8-S10 render lock) does not exist — `run_pipeline` is
still one monolithic function, and WP11's own report already confirmed the
standalone S1-S4 modules (`v16_research`/`v16_script`) aren't wired into
it. Splitting it to make a real lock-based overlap possible is bigger than
`v16_batch.py`'s file scope and risks the pipeline every prior WP's render
proof depends on. `run_batch` stays sequential; `lanes_overlap: False` is
in every batch report so this is visible, not assumed done.
